# 完整备份、自动保留与隔离恢复

## 1. `.sttbackup` 容器

完整备份是 UTF-8 ZIP 容器，扩展名固定为 `.sttbackup`，根目录包含：

- `backup-manifest.json`：备份 ID、原因、来源项目 ID/名称、Revision、应用版本、Schema 版本和文件清单；
- `project/manifest.json`；
- `project/project.sqlite3`；
- `project/attachments/`；
- `project/artifacts/`。

文件清单逐项记录 POSIX 相对路径、SHA-256 和字节数。容器不写入工作区绝对路径、账号令牌、许可证凭证或设备私钥。

## 2. 一致性生成

备份不会直接复制活动 WAL 数据库。sidecar 使用 SQLite Backup API 生成一致性数据库副本并执行 `PRAGMA integrity_check`，再复制项目 manifest、附件和算法/导出制品。ZIP 先写到同目录随机临时文件，完成以下校验后才原子改名：

- 文件数不超过 20,000；
- 解压总量不超过 5 GiB；
- 单项压缩比不超过 1,000；
- 无绝对路径、反斜杠、驱动器路径、`.`/`..` 或符号链接；
- ZIP 实际文件集合与 manifest 完全相等；
- 每个文件的大小和 SHA-256 一致。

生成成功后才写 `backup_records`。手工“另存一份”也先生成项目内已验证副本，再通过原生保存对话框原子复制到用户选择的位置。

## 3. 自动策略

- 每个本地自然日首次成功业务保存后创建一份 `daily` 备份；
- 删除实体前强制创建 `pre-destructive` 备份；
- 后续批量导入确认会强制创建 `pre-import` 备份；
- 自动备份默认只保留最近 10 份；
- 用户标记“长期保留”的备份不参与自动清理；
- 清理仅允许删除 `backups/<当前项目ID>/` 下、扩展名为 `.sttbackup` 且数据库记录精确指向的文件。

业务保存已经提交但每日备份失败时，接口返回安全警告，不谎报业务保存失败；删除前备份失败则阻止删除。

## 4. 隔离恢复

恢复始终创建新的项目 ID 和项目目录，不覆盖当前项目：

1. 用户选择项目内备份记录或外部 `.sttbackup`，界面显示准确路径并二次确认；
2. sidecar 重新执行 ZIP 路径、数量、体积、压缩比、清单和哈希校验；
3. 更高 Schema 版本直接拒绝，禁止向下迁移；
4. 只解压到工作区 `temp/restore-*` 随机隔离目录；
5. 对 SQLite 执行完整性、外键、Schema 和 Revision 检查；
6. 分配新项目 ID、设置恢复名称并原子移动到 `projects/<新ID>`；
7. 使用正常项目打开流程做最终检查；失败时只清理本次新建目标，原项目和备份保持不变；
8. 验证通过后切换桌面端当前项目。

恢复接口要求 `confirmed=true`，客户端无法绕过服务端确认门槛。

## 5. 本地接口

- `POST /v1/backups`：创建并验证完整备份；
- `GET /v1/backups`：列出备份、保留状态、文件存在性和大小；
- `POST /v1/backups/{id}/verify`：重新验证 ZIP 与记录 SHA-256；
- `PUT /v1/backups/{id}/retained`：设置或取消长期保留；
- `POST /v1/backups/restore`：从记录或外部文件恢复为新副本。

## 6. 验证结果

自动测试覆盖：

- 含候选和课表的项目完整备份、外部复制、记录哈希复核和恢复；
- 恢复后实体数、候选数、课表数、Revision、完整性和外键与来源一致；
- 来源项目 ID 与数据不被修改，恢复项目获得新 ID；
- ZIP 路径穿越和文件篡改被拒绝；
- 每日备份同一自然日只创建一次；
- 自动备份只保留最近 10 份且长期保留不被删除；
- Python 全量测试、Vue 生产构建和 Rust 编译检查通过。
