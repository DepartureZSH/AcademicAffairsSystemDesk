# 实施、测试与验收计划

> 本文从“文档已经批准”开始安排后续实施。各 Gate 只约束依赖它的工作流，不再把所有外部服务准备项设为桌面主体开发的总前置条件。

## 2. 阶段 0：首次执行

本次只允许：

- 新增和评审 `docs/desktop/*.md`。
- 读取仓库状态并记录现有风险。
- 不修改业务代码、数据库迁移、CI、部署配置和已有文档。
- 不创建签名证书、不生成生产密钥、不连接或更改线上系统。

完成后只等待 G0 的最小本地条件。G1 至 G3 可随项目推进逐阶段准备。

## 3. 阶段 2：建立可重复代码基线

1. 保存 `git status --short` 和 `git diff --stat`。
2. 逐项确认当前已修改的 Supabase migrations、算法测试和 `.bck/.tmp` 文件归属。
3. 由用户决定哪些内容提交、忽略或另行归档；禁止直接丢弃现有修改。
4. 在主线形成可追溯的基线提交后创建 `codex/desktop-local`。
5. 固定 Node、Rust、Python 和 Supabase CLI 版本，并生成依赖锁文件。
6. 安装 OR-Tools 等缺失依赖，执行：

```powershell
python -m pytest -q
Set-Location apps/web-admin
npm ci
npm run build
```

7. 记录基线测试数量、耗时和已批准的跳过项；不得把“测试未收集”视为通过。

## 4. 阶段 3：开源与合规

新增：

- 根目录 Apache-2.0 `LICENSE` 和 `NOTICE`。
- `PRIVACY.md`、`SECURITY.md`、`TRADEMARKS.md`、`CODE_SIGNING_POLICY.md`。
- 贡献指南、漏洞私下报告渠道和第三方资产来源清单。
- UI 中“关于”页面，显示版本、许可证、官方签名发行说明和隐私链接。

审计所有随安装包分发的字体、图标、图片、Python 模块、原生库和模型文件。不能证明可再分发的资产必须替换或排除。官方名称、图标和安装包不得暗示第三方构建由杭州格若时科技有限公司或 SignPath Foundation 背书。

## 5. 阶段 4：Karios Pay 加固（并行工作流，受 G1 约束）

实施顺序：

1. 定义版本化 `/v1` 服务接口、项目身份和权限范围。
2. 实现 HMAC 请求签名、时间窗、nonce 防重放和速率限制。
3. 使 `businessOrderId` 成为项目内唯一合同，并实现支付创建幂等。
4. 由许可证平台签发权威产品/金额断言；支付服务拒绝任意客户端价格。
5. 为支付和退款实施不可逆状态迁移与数据库约束。
6. 增加出站事件 outbox、签名回调、重试、死信和人工重放。
7. 通过唯一事件 ID 与订单唯一约束保证下游履约一次。
8. 增加对账、指标、敏感字段脱敏和告警。

先用支付服务 mock 完成自动测试，再用明确标记的 1 分测试产品执行真实回归。生产产品价格不能复用测试配置。

## 6. 阶段 5：许可证平台（并行工作流，受 G1 约束）

### 6.1 数据与服务

- 新增私有 `license` schema、RLS 测试和最小数据库函数。
- 实现购买会话、订单、支付 webhook、激活、续签和当前设备停用函数。
- 部署 `license-worker`，处理 SMTP outbox、风险清理和对账任务。
- 为许可证 Ed25519 公钥建立 `kid` 轮换协议，客户端同时接受当前和上一个公钥。
- 修复现有 API 中未验证 JWT 签名的路径；所有新接口不得复用不安全解析。

### 6.2 Web

- `dean.karios.site/purchase`：消费一次性会话、显示权威产品、二维码、轮询和安全提示。
- `dean.karios.site/license-ops`：独立权限、强制 AAL2、运营审计和敏感字段掩码。
- 登录和注册页面增加隐私、许可证和 IP 风控说明。

## 7. 阶段 6：桌面基础（G0 后可开始）

1. 在仓库中建立桌面应用目录和 Tauri 2 配置。
2. 固定 bundle identifier 为 `tech.karios.stt.desktop`，产品名为“时奕教务排课”。
3. 提取当前 Vue 的桌面可复用组件，建立 web/desktop 数据访问适配层。
4. 接入安全存储、设备密钥、登录、激活和离线授权门禁。
5. 封装 Python sidecar，建立协议版本、健康检查和异常恢复。
6. 建立本地 SQLite repository、schema migration 和工作目录。
7. 完成 `.sttproj`、`.sttbackup`、自动备份和恢复。
8. 添加 Tauri updater，但默认只指向测试 channel。

## 8. 阶段 7：功能迁移顺序（不依赖 G1 至 G3）

每个模块都按“领域模型 → 本地 API → UI 适配 → 导入导出 → 单元/集成测试”闭环，不并行维护两套含义不同的数据模型。

1. 学期、作息、年级、班级。
2. 教师、科目、教室和教室类型。
3. 课程计划、教学任务和课次。
4. 可用性与约束模板、约束编译和预检。
5. 手工排课和即时冲突校验。
6. 自动排课首轮、取消和进度事件。
7. warm start 后续轮次、候选比较和评分解释。
8. 班级/教师/教室/年级课表。
9. Excel、CSV、PDF、problem XML 和 solution XML。

AI、机构、成员、平台审核组件不进入桌面路由或安装包。

## 9. 测试策略

### 9.1 自动测试层级

- Rust：安全存储适配、JWS 校验、时钟策略、sidecar 生命周期、路径安全和更新校验。
- TypeScript/Vue：授权状态机、购买跳转、表单、导入预览、候选比较和路由排除。
- Python：repository、迁移、XML 映射、约束编译、求解器、取消、归档和备份。
- PostgreSQL：状态约束、幂等、一笔订单一次发证、RLS、AAL2 和审计不可改写。
- Edge/worker：签名、nonce、限流、密钥 HMAC、邮件加密/删除、续签和对账。
- 端到端：真实桌面进程、浏览器购买页、Supabase 测试环境和支付 mock。

### 9.2 必测安全场景

- 修改、过期、错误 audience、错误设备和未知 `kid` 的授权 JWS。
- 系统时钟向前/向后调整、离线第 6 天和第 8 天。
- 同密钥其他账号激活、第四台设备激活、已撤销设备续签。
- 原始密钥出现在日志、数据库、崩溃包、浏览器存储或网络 URL 的扫描。
- 其他用户读取订单/许可证、普通管理员访问运营接口、AAL1 运营员操作。
- webhook 伪造、重放、乱序、错误金额、重复 `SUCCESS` 和事务中途失败。
- ZIP 路径穿越、符号链接、超大解压、损坏 SQLite 和更高 schema 版本。
- 恶意网页调用 Tauri 命令或本机 sidecar。

### 9.3 数据与算法场景

- 最小项目、空数据、单双周、连堂、多教室、教师不可用和跨天边界。
- 可行 6000 课次确定性合成项目。
- 教师课时总量超过可用时段、教室容量不足、互斥硬约束等不可行项目。
- 同随机种子重现、不同种子探索、父候选 warm start 和取消恢复。
- Excel/CSV 往返、XML 往返、PDF/Excel 版式和中文文件名。

## 10. 验收矩阵

| 编号 | 场景 | 通过标准 |

| LIC-01 | 年付许可证首次激活 | 账号绑定正确，设备数 +1，返回 7 天 JWS |

## 11. 缺陷与发布规则

- P0：数据丢失、密钥泄漏、越权、错误发证、支付金额错误、安装器不可用。存在任一 P0 禁止发布。
- P1：核心流程不可用、候选错误、恢复失败、授权误拒绝。存在任一未批准 P1 禁止发布。
- P2：有规避方案的非核心问题，可记录负责人和目标版本后发布。
- 每个发布候选必须保存构建来源、依赖清单、测试报告、SBOM、安装包哈希和签名验证结果。

## 12. 当前已知基线风险

- 工作区存在大量已有 Supabase migration 修改和临时/备份文件，进入阶段 2 前必须由用户确认归属。
- 当前前端构建已通过；隔离 Python 环境已安装 OR-Tools 9.15.6755，测试结果为 180 通过、2 失败，失败原因是实现新增 `period_index` 而旧断言尚未同步，需在代码基线阶段处理。
- 当前仓库已公开并采用 Apache-2.0，但尚未完成隐私/安全/商标/签名政策、可验证构建和既有公开发行，暂不满足 SignPath Foundation 的全部申请条件。
- Karios Pay 当前缺少生产多项目使用所需的端到端幂等、权威定价和服务鉴权。
- Sealos 自托管 Supabase 的备份、Edge Runtime、Cron、Vault/secret 和可信代理能力需在预发布环境实际验证。

## 13. 当前停止点

文档基线完成后，只需确认《06-计划开始前人工准备清单》的 G0，即可开始本地桌面主体实施。G1、G2、G3 未完成不会阻塞本地数据层、排课算法、桌面壳和业务流程迁移；它们分别只阻塞远程授权/支付接入、测试签名发布和 SignPath 正式发布。确认某一 Gate 不代表授权修改生产系统，相关目标环境仍需在进入该工作流时单独核对。
