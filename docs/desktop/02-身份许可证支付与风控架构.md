# 身份、许可证、支付与风控架构

> 2026-09-05 更新：当前发布目标已改为「同账号会员联网校验」，不再采用本文中的激活码和七天离线方案。以 [58-账号会员联网授权](58-账号会员联网授权.md) 为准；下文保留为历史设计。

> 适用环境：Sealos 自托管 Supabase + Karios 微信支付 + `dean.karios.site` 购买/运营页面。
> 核心原则：远端只验证“谁可以使用官方发行版”，不接收任何教务业务数据。

## 1. 安全目标与非目标

### 1.1 安全目标

- 邮箱密码确认用户身份，企业密钥确认购买权益，设备私钥确认当前设备。
- 每次支付最多履约一次，错误金额、伪造状态、重复通知和乱序通知不得发证。
- 原始企业密钥、服务密钥、签名私钥和 SMTP 密码不以明文持久化。
- 许可证被退款、暂停或撤销后不能继续在线续签，离线授权最多残留 7 天。
- 普通用户、购买页和桌面客户端均不能读取许可证私有表或执行运营操作。
- IP 风险信号用于限流和人工复核，不能单独作为撤销许可证的证据。

### 1.2 非目标

- 不以许可证系统保护开源源码不被修改。
- 不采集稳定硬件序列号，不实施内核驱动或侵入式反调试。
- 不在远端保存或分析排课业务数据。
- 不用用户可写的 `user_metadata` 作为管理员或授权依据。

## 2. 组件与信任边界

```text
桌面应用 ──Supabase Auth/JWT──> Sealos Supabase
    │                               ├─ Auth
    │                               ├─ Postgres 私有 license schema
    │                               ├─ Edge Functions
    │                               └─ Cron / 对账任务
    │
    └─系统浏览器──> dean.karios.site/purchase
                           │
                           └─已认证服务调用──> pay.karios.site
                                                  │
                                                  └─微信支付

Karios 签名回调 ──> Supabase Edge Function ──> 一次性发证事务
                                              └─邮件 outbox
Sealos 内网 license-worker ──SMTP TLS──> 企业邮箱服务
```

### 2.1 客户端允许持有

- Supabase URL、publishable key、短期用户 JWT。
- 设备私钥、设备随机 ID、授权 JWS。
- 掩码许可证信息和到期时间。

### 2.2 只允许服务端持有

- Supabase secret/service-role key。
- `LICENSE_KEY_PEPPER`、邮件 AES 密钥、授权 Ed25519 私钥。
- Karios 项目服务凭据和 webhook HMAC 密钥。
- SMTP 主机、用户名、密码和发件地址。

所有服务端秘密使用 Sealos Secret 注入，不写入镜像、仓库、构建参数或日志。

## 3. 身份模型

- Supabase Auth 为唯一身份源，主键使用 `auth.users.id`。
- 注册要求邮箱确认；生产环境必须使用企业自定义 SMTP。
- 桌面登录成功不等于可进入业务界面，还必须存在当前设备的有效授权。
- refresh token 由 Tauri 安全存储适配器管理，Vue 不写入 `localStorage`。
- 新许可证接口必须真正验证 JWT 签名、issuer、audience、expiry；禁止沿用 `get_unverified_claims` 类逻辑。
- 许可证运营人员记录在独立的 `license.operators` 表，由服务端管理，并要求 JWT 的认证保障级别达到 AAL2。

## 4. 许可证与订单数据模型

许可证表位于不暴露给 PostgREST 的私有 schema。若必须暴露只读视图，应单独授权并启用 RLS。

| 表 | 关键字段与约束 |
| --- | --- |
| `license.products` | `code` 唯一、服务端价格（分）、币种、期限天数、设备数、启用状态 |
| `license.purchase_sessions` | 用户、随机令牌 HMAC、5 分钟过期、单次消费时间 |
| `license.orders` | 用户、产品、权威金额、状态、`business_order_id` 唯一、支付单号唯一 |
| `license.payment_events` | provider event ID 唯一、签名校验结果、状态、最小化载荷摘要 |
| `license.licenses` | 用户、产品、key HMAC、掩码前缀、状态、开始/到期时间、授权版本 |
| `license.devices` | 许可证、随机设备 ID、公钥、指纹、状态、首次/最后确认时间；活动设备唯一 |
| `license.entitlement_events` | JTI、设备、签发/过期、结果码和授权版本，不保存完整 JWS |
| `license.email_outbox` | 模板、收件人、密钥临时密文、尝试次数、下次执行时间、投递状态 |
| `license.risk_events` | 账号、设备、IP、网段 HMAC、应用版本、结果和到期清理时间 |
| `license.risk_flags` | 风险类型、分数、状态、处置人和处置原因 |
| `license.operators` | 用户、权限范围、启用状态、授予人和时间 |
| `license.admin_audit` | 只追加；操作人、动作、对象、原因、前后状态和时间 |

状态约束：

- 订单：`PENDING -> PAID | CLOSED | FAILED`，`PAID` 不得回退。
- 许可证：`PENDING_EMAIL -> ACTIVE -> EXPIRED | SUSPENDED | REVOKED | REFUNDED`。
- 设备：`ACTIVE -> DEACTIVATED | REVOKED`，重新激活创建新事件，不复写历史。
- 邮件：`PENDING -> PROCESSING -> SENT | RETRY | DEAD`。

写入支付事件、订单改为已支付、创建许可证和写入发件箱必须在同一数据库事务中完成。`orders.id` 对 `licenses.order_id` 建唯一约束，从数据库层保证一次履约。

## 5. 企业密钥

### 5.1 格式与生成

- 使用密码学安全随机源生成至少 160 位熵。
- 用户可见格式建议为 `STT1-XXXXX-XXXXX-XXXXX-XXXXX-XXXXX-XXXXX-XX`，包含版本和校验字符。
- 比较前只进行大写、移除分隔符和校验码验证，不做模糊匹配。

### 5.2 服务端存储

```text
lookup = HMAC-SHA-256(LICENSE_KEY_PEPPER, normalized_key)
```

数据库保存 `lookup`、显示前缀、末四位、版本和轮换序号。pepper 轮换使用版本化密钥环；旧 pepper 只保留到相关许可证全部轮换完成。

为可靠发信，原始密钥仅在发件箱中短暂以 AES-256-GCM 密文存在：

- 每条记录使用随机 96 位 nonce。
- AAD 包含 outbox ID、用户 ID、许可证 ID 和密钥版本。
- SMTP 明确接受邮件后立即在事务中清空密文、nonce 和 tag。
- 进入死信队列后，管理员“重发”必须生成新密钥并使旧 HMAC 失效。

任何 API 响应和运营页面都不得返回原始密钥。

## 6. 设备激活与离线授权

### 6.1 设备身份

- 首次启动生成 Ed25519 设备密钥对和随机设备 ID。
- 私钥进入 Stronghold/系统凭据库；公钥提交服务端。
- 不采集 CPU、主板、硬盘序列号。卸载后重装可能占用新设备名额，由运营页审计撤销旧设备。

### 6.2 首次激活

1. 客户端带有效 Supabase JWT 请求服务端 nonce。
2. 客户端签署 `nonce + user_id + device_id + app_id + timestamp`。
3. 提交签名、公钥、设备 ID、应用版本和原始企业密钥。
4. 服务端校验 JWT、nonce 单次性、时间窗、密钥 HMAC、账号绑定和活动设备数。
5. 在事务中创建/恢复设备并写审计事件。
6. 返回设备绑定的授权 JWS；请求结束后清空原始密钥内存缓冲。

### 6.3 授权 JWS

使用服务端 Ed25519 私钥签名，客户端内置可轮换的公钥集。最低 claims：

| claim | 说明 |
| --- | --- |
| `iss` | 固定许可证服务发行者 |
| `aud` | `tech.karios.stt.desktop` |
| `sub` | Supabase 用户 ID |
| `license_id` | 许可证 ID |
| `device_id` | 当前设备 ID |
| `cnf.jkt` | 设备公钥指纹 |
| `plan` | 产品代码 |
| `entitlement_version` | 撤销和轮换版本 |
| `iat/nbf/exp` | 签发、生效和不超过 7 天的到期时间 |
| `jti` | 唯一授权事件 ID |

客户端验证签名、audience、时间、设备指纹和本地最近可信服务器时间。系统时间向过去回拨超过 5 分钟时要求在线重新核验。

### 6.4 续签与失效

- 在线启动、每天首次运行以及剩余有效期不足 48 小时时尝试续签。
- 续签需要用户 JWT、服务端 nonce 和设备签名，不需要企业密钥。
- 网络错误可回退到未过期本地授权；`SUSPENDED/REVOKED/REFUNDED/ACCOUNT_MISMATCH` 等明确业务拒绝不可回退。
- 用户主动退出时清除 Supabase 会话和本地授权，但保留设备私钥以便同账号重新登录。

## 7. 购买会话与支付流程

### 7.1 外部购买会话

1. 已登录桌面端调用 `create-purchase-session`。
2. 服务端生成 256 位随机令牌，只保存 HMAC，5 分钟过期且单次使用。
3. Tauri 打开 `https://dean.karios.site/purchase#session=<token>`；令牌放在 URL fragment，避免进入服务器访问日志和 Referer。
4. 页面把令牌 POST 到服务端换取短期购买上下文，随后从地址栏移除 fragment。
5. 页面只提交产品代码，不能提交金额、用户 ID 或付款状态。

### 7.2 创建 Native 订单

- Supabase 读取启用的产品和权威价格，先创建业务订单。
- 调用 Karios Pay 时使用项目服务鉴权、timestamp、nonce、请求签名和幂等键。
- 发送 `businessOrderId`、权威金额、描述和经过签名的项目上下文。
- 保存返回的 `outTradeNo`；页面只获得二维码 `codeUrl`、掩码订单号和过期时间。
- 页面约每 3 秒查询项目后端的订单状态，不直接以浏览器返回或微信桥消息发证。

### 7.3 Karios Pay 上线前 P0 加固

- 项目级服务凭据与权限范围。
- HMAC 请求签名，覆盖方法、路径、body hash、timestamp 和 nonce；5 分钟防重放窗口。
- `businessOrderId` 唯一语义和支付创建幂等键。
- 项目端权威价格断言，拒绝任意客户端金额。
- 严格状态迁移，`PAID` 不回退。
- 签名出站事件、指数退避、outbox、死信与人工重放。
- 事件 ID 去重和下游一次性履约。
- 退款、关单和实时查询只允许可信服务调用。
- CORS 精确白名单和按项目/IP 的速率限制。

上述项目完成并通过测试前，只允许测试订单，不启用生产自动发证。

### 7.4 支付回调与发证

`karios-payment-webhook` 必须：

1. 从原始请求体校验 HMAC、timestamp、nonce 和项目 ID。
2. 以 provider event ID 去重；重复事件返回成功但不重复执行。
3. 锁定业务订单，核对 `businessOrderId`、`outTradeNo`、币种、金额和当前状态。
4. 只接受 Karios 已向微信确认的 `SUCCESS`。
5. 在单事务内标记订单、创建许可证、创建邮件 outbox 和审计记录。
6. 事务提交后返回 2xx；失败由 Karios outbox 重试。

Supabase 定时任务对长时间 `PENDING` 订单进行只读查询和补偿。对账不得把浏览器提交的数据作为支付成功证据。

## 8. 邮件任务服务

`license-worker` 部署在 Sealos 内网，使用受限数据库函数领取 outbox，不直接向公网暴露管理端口。

- 使用 `FOR UPDATE SKIP LOCKED` 或等价原子领取机制。
- 单次 SMTP 调用设置连接、发送和总超时。
- 暂时性错误指数退避并加随机抖动；默认最多 8 次。
- 永久性地址错误进入死信，禁止无限重试。
- 邮件主题和模板不得在日志中插入原始密钥。
- `Message-ID` 由 outbox ID 确定生成，方便追踪和抑制重复。
- 指标仅记录发送状态、耗时、提供商响应分类和队列深度。

Supabase 项目内置的默认 SMTP 不适合生产。生产必须配置企业自定义 SMTP，并完成 SPF、DKIM、DMARC 和发件域验证：<https://supabase.com/docs/guides/auth/auth-smtp>。

## 9. 许可证运营页

路径建议为 `https://dean.karios.site/license-ops`。前端隐藏入口不是权限控制，所有接口必须执行：有效 JWT → `aal2` → `license.operators` 权限检查。

首版操作：

- 按订单号、邮箱、许可证 ID 或密钥掩码查询。
- 查看订单、支付事件、许可证、设备、邮件和风险时间线。
- 暂停/恢复许可证，撤销设备。
- 在填写原因后转移许可证账号。
- 轮换并重发企业密钥。
- 发起幂等退款并跟踪最终结果。
- 处理、忽略或升级风险标记。

敏感操作需要二次确认、理由和审计；转移、退款、轮换密钥建议再次验证管理员 MFA。页面不得显示完整密钥、JWT、SMTP 响应正文或完整支付载荷。

## 10. 风控和数据保留

### 10.1 记录字段

- 可信代理解析出的客户端 IP。
- IP `/24`（IPv4）或 `/56`（IPv6）网段的 HMAC。
- 用户、许可证、设备、公钥指纹、应用版本、接口和结果码。
- 时间、请求 correlation ID、限流命中和人工处置。

禁止记录密码、原始密钥、access/refresh token、Authorization、Cookie、学校数据和导入文件名。

### 10.2 默认规则

| 规则 | 默认动作 |
| --- | --- |
| 同许可证超过 3 台活动设备 | 拒绝新增设备 |
| 同账号/设备/IP 1 小时内 10 次密钥失败 | 限流 1 小时 |
| 24 小时内出现 5 个以上不同网段 | 暂停新增设备并创建人工风险标记 |
| webhook 签名错误或重放 | 拒绝、告警，不改变订单 |
| IP 异常但设备签名有效 | 记录风险，不单独撤销现有设备 |

完整 IP 默认保留 30 天；网段 HMAC 和风险聚合保留 180 天；到期任务每天清理。订单、退款和财务记录的期限由正式财务与法律政策另行确认。

## 11. RLS 与服务端函数要求

- 许可证 schema 默认不加入 PostgREST 暴露列表。
- 用户只通过经过验证的 Edge Function 查看自己的掩码许可证和当前设备。
- 管理端写操作不得开放为可由普通 authenticated role 直接执行的表操作。
- 所有 `SECURITY DEFINER` 函数固定空或明确 `search_path`，使用 schema 限定对象名，并撤销 public execute。
- service-role 只存在于 Edge Function/worker，不进入 Vue 构建。
- migration 同时包含 RLS 测试：匿名、其他用户、本人、非 AAL2 运营员和 AAL2 运营员。

## 12. 接口错误码

| 错误码 | 客户端行为 |
| --- | --- |
| `AUTH_REQUIRED` | 显示登录页 |
| `EMAIL_NOT_CONFIRMED` | 提供重发验证邮件 |
| `PURCHASE_SESSION_EXPIRED` | 重新从桌面打开购买页 |
| `LICENSE_KEY_INVALID` | 不泄漏账号/密钥哪一项错误，计入限流 |
| `LICENSE_ACCOUNT_MISMATCH` | 提示联系购买账号或客服 |
| `DEVICE_LIMIT_REACHED` | 显示额度和客服撤销指引 |
| `ENTITLEMENT_REVOKED` | 立即锁定业务入口 |
| `ONLINE_CHECK_REQUIRED` | 显示联网和时钟检查指引 |
| `PAYMENT_PENDING` | 继续轮询，不判定失败 |
| `PAYMENT_AMOUNT_MISMATCH` | 冻结订单并告警，不发证 |
| `OPERATOR_AAL2_REQUIRED` | 引导运营员完成 MFA |

## 13. 上线门槛

- [ ] 自托管 Supabase Auth、JWT 校验、RLS 和 MFA 测试通过。
- [ ] Karios Pay 的 P0 加固全部完成。
- [ ] 重复、乱序、错误金额和伪造 webhook 均不能发证。
- [ ] 原始密钥只在受控内存和短期加密 outbox 中出现。
- [ ] SMTP 成功后密钥密文已删除；失败可安全轮换重发。
- [ ] 三设备上限、离线 7 天、退款和撤销行为符合规格。
- [ ] 浏览器和桌面构建中不存在 secret/service-role。
- [ ] 网络与日志审计确认无教务业务数据外传。
- [ ] IP 保留和隐私说明已完成人工法律审核。
