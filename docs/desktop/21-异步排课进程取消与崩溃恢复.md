# 异步排课进程、取消与崩溃恢复

## 1. 进程边界

每个自动排课轮次分为三个阶段：

1. sidecar 主进程创建不可变数据快照、编译 Problem XML 并记录轮次；
2. 独立本机算法工作进程读取 Problem XML 和临时配置，运行 OR-Tools CP-SAT，并只原子写出结果信封；
3. sidecar 主进程重新验证完整结果，在单个 SQLite 事务中写入候选、课表条目、指标、轮次状态和最终事件。

算法工作进程不打开项目数据库、不持有 Supabase 凭据、不访问网络，也不能直接创建可见候选。命令行参数只有本地文件路径和轮次 ID；warm start 等业务输入写入项目内部临时文件，完成后删除。

Windows 打包入口调用 `multiprocessing.freeze_support()`，确保冻结后的 Python sidecar 能安全派生算法工作进程。

## 2. 异步状态和界面

`POST /v1/scheduling/rounds` 完成输入编译并启动工作进程后立即返回，通常状态为 `solving`。界面每秒读取轮次与候选列表，显示准备、求解、验证和完成状态；进度条按阶段与时间预算展示估算进度，不把估算值伪装为 OR-Tools 的确定完成百分比。

同一 sidecar 同时只运行一个算法工作进程。运行期间禁止关闭、切换、恢复或导入项目，普通状态查询仍可响应。算法全程不访问远程身份或许可证服务。

## 3. 取消

`POST /v1/scheduling/rounds/{id}/cancel` 执行以下流程：

1. 标记当前作业收到取消请求；
2. 请求终止算法工作进程；
3. 最多等待 5 秒；
4. 若仍未退出，强制结束该工作进程，但不结束 Tauri 或 sidecar 主进程；
5. 将轮次标记为 `cancelled` 并追加 `round_cancelled` 事件；
6. 删除临时请求和结果文件。

取消与正常完成发生竞争时，以已经完成验证并提交的候选为准；一旦轮次不再处于 `solving`，迟到结果会被拒绝。取消轮次不创建候选，也不修改既有父候选。

## 4. 原子候选可见性

Solution XML 先写入原子文件。候选主记录、全部课表条目、指标、轮次成功状态和 `candidate_persisted` 事件随后进入同一个 `BEGIN IMMEDIATE` 事务。任何数据库写入失败都会回滚整批记录，因此界面只能看到完整候选或完全看不到候选；可能残留的未引用 Solution 文件不构成可见业务数据，并可由后续维护清理。

## 5. 崩溃恢复

打开已有项目、恢复备份或导入 `.sttproj` 时，应用检查遗留的 `queued/preparing/solving/validating` 轮次，将其改为 `failed_recoverable`，错误码为 `INTERRUPTED_ON_RESTART`，并追加失败事件。用户可以从上一个完整候选重新发起轮次。

工作进程作为 sidecar 的守护子进程管理。即使异常退出后留下临时结果，它也没有数据库写权限；重启后的恢复门禁还会拒绝迟到结果，因而不会把半成品恢复成候选。

## 6. 自动验证

测试覆盖：

- 真实 OR-Tools 独立进程运行时主进程仍能读取 `solving` 状态；
- 子进程完成后生成完整候选和全部课表条目；
- 可控慢工作进程可在 5 秒门限内取消，候选数量保持为零；
- 中断状态在恢复检查后变为 `failed_recoverable`；
- 已结束轮次拒绝迟到求解结果；
- 同步服务路径仍保留，用于算法单元测试和离线诊断。
