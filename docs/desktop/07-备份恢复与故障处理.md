# 备份、恢复与故障处理手册

> 覆盖本地项目、Sealos Supabase、许可证/支付链路、密钥和更新事故。所有恢复先隔离副作用，再恢复数据，最后逐项重新启用服务。

## 1. 恢复目标

| 对象 | 建议 RPO | 建议 RTO | 说明 |
| --- | --- | --- | --- |
| 本地活动项目 | 最近一次成功保存/关键操作前备份 | 30 分钟 | 用户自行恢复到新副本 |
| Supabase 身份/许可证库 | 24 小时以内；正式运行后评估缩短 | 4 小时 | 每日逻辑备份 + 平台快照 |
| 支付事件/outbox | 尽量接近 0 | 2 小时 | Karios 和 Supabase 双方持久化、可对账 |
| 签名/许可证密钥 | 不允许仅有单份 | 4 小时 | 加密离线备份和双人恢复 |
| 更新 manifest | 上一个有效版本 | 30 分钟 | 保留不可变历史 manifest |

正式上线前由负责人批准实际 RPO/RTO；表中数值是首版最低目标。

## 2. 本地项目备份

### 2.1 自动备份触发

- schema 迁移前。
- 批量导入确认前。
- 大规模删除、项目恢复或候选重建前。
- 每个自然日首次成功保存后。
- 用户手工执行。

备份使用 `.sttbackup`，先写入随机临时文件，完成 SQLite checkpoint、manifest、SHA-256 和解压测试后再原子改名。失败备份不得参与保留计数。

### 2.2 保留与空间

- 每项目保留最近 10 份成功自动备份。
- 用户标记“保留”的备份不自动删除。
- 可用空间不足时停止产生新大文件并提示清理，不删除最后一份有效备份。
- 只清理 manifest 归属于当前项目且位于已验证备份根目录的文件。

## 3. 本地恢复操作

1. 关闭活动项目并等待 sidecar 完全退出。
2. 复制损坏项目目录到隔离位置，不在原目录上试错。
3. 在应用“恢复备份”中选择 `.sttbackup`。
4. 校验扩展名、容器格式、路径安全、manifest、SHA-256 和大小上限。
5. 解压到新的随机临时目录。
6. 执行 `PRAGMA integrity_check`、外键检查和 schema 兼容检查。
7. 将恢复结果作为新项目副本打开，例如“项目名（恢复 2026-08-30）”。
8. 对比实体计数、最近候选、关键课表和导出。
9. 用户确认后再归档旧损坏项目；不得自动覆盖或删除。

若备份来自更高应用版本，停止恢复并提示先升级应用。不得尝试向下迁移 SQLite。

## 4. 本地常见故障

### 4.1 sidecar 无法启动

检查顺序：

1. 当前许可证/离线授权是否有效。
2. sidecar 文件是否存在且 SHA-256 与安装清单一致。
3. Windows 防病毒是否隔离文件。
4. 随机回环端口是否能绑定。
5. sidecar 协议版本是否与 Tauri 匹配。
6. 收集脱敏启动日志；禁止让用户关闭系统安全软件作为长期解决方案。

### 4.2 数据库被锁定

- 确认没有第二个应用实例或遗留 sidecar。
- 不直接删除 WAL/SHM 文件。
- 正常终止遗留进程后重新打开；仍失败则复制项目并使用备份恢复。

### 4.3 磁盘写满或应用崩溃

- 停止导入/求解，不继续写临时文件。
- 保留原数据库、WAL 和临时文件供诊断。
- 释放其他磁盘空间后从最近有效备份恢复到新目录。
- 执行完整性检查和课表抽样，不把能打开等同于数据完整。

### 4.4 授权离线过期

- 检查系统时间、HTTPS、Supabase 域名和代理。
- 不修改本地文件伪造延长授权。
- 恢复网络后重新登录/续签；明确服务端撤销时联系许可证运营员。
- 项目文件不因授权过期删除，恢复授权后可继续打开。

## 5. Supabase 备份

### 5.1 内容

- Auth 所需 schema 和配置记录。
- public 中的用户映射/管理员表。
- 私有 `license` schema、函数、RLS/grant 和 migration 历史。
- Edge Function 源码由 Git 管理，不以数据库备份代替。
- Sealos Secret 只备份到独立密码管理/密钥托管系统，不进入数据库 dump。

### 5.2 最低流程

1. 由受限备份用户执行一致性逻辑备份。
2. 在备份主机侧立即加密并生成 SHA-256。
3. 上传到与 Sealos 主集群故障域不同的受控存储。
4. 写入备份时间、数据库版本、migration 版本、大小和哈希。
5. 每周校验可下载、可解密；每月恢复到隔离环境。

具体 `pg_dump/pg_restore` 参数必须按实际自托管 Supabase PostgreSQL 版本和官方备份建议在预发布验证后固化。禁止在命令行明文传递数据库密码。

## 6. Supabase 恢复演练

### 6.1 隔离

恢复前必须：

- 使用新的隔离 namespace、数据库和域名。
- 禁止公网支付 webhook。
- 禁止 license-worker 发信和对账。
- 使用测试 SMTP 或完全阻断 SMTP 出站。
- 不加载生产支付和签名 secret。

### 6.2 恢复与验证

1. 部署与备份匹配的 PostgreSQL/Supabase 版本。
2. 解密并验证 SHA-256。
3. 恢复角色、schema、数据和权限。
4. 检查 migration 版本、扩展、函数 owner、grant 和 RLS。
5. 统计 Auth 用户、订单、许可证、设备、outbox 和审计记录。
6. 使用隔离测试账号验证登录、本人查询、其他用户拒绝、运营 AAL2。
7. 检查已支付订单与许可证一一对应，无重复活动许可证。
8. 将旧 pending/outbox 保持暂停，避免测试环境产生真实副作用。
9. 记录恢复耗时、差异和改进项。

### 6.3 生产恢复

只有隔离验证通过后才能决定生产恢复点。生产恢复顺序：数据库 → 只读验证 → Auth → 用户许可证查询 → webhook → worker → 对账。每启用一层先观察错误率和队列，再启用下一层。

## 7. 支付和发证故障

### 7.1 用户已付款但未发证

1. 以 `businessOrderId/outTradeNo` 查询 Karios 服务和微信最终状态。
2. 若微信未确认 `SUCCESS`，保持 pending，不人工伪造支付成功。
3. 若 Karios 为 SUCCESS，检查签名 webhook outbox、投递次数和响应码。
4. 在运营页使用原事件 ID 执行幂等重放。
5. 数据库唯一约束保证已有许可证时返回原结果，不创建第二张。
6. 若许可证已创建但邮件失败，轮换密钥并重新入队，不展示旧明文。

### 7.2 重复回调或乱序状态

- 按 provider event ID 去重。
- `PAID` 不允许回退到 `PENDING/NOTPAY`。
- 重复 SUCCESS 返回 2xx 幂等确认。
- 状态冲突进入人工对账，不自动改变许可证。

### 7.3 金额不一致

- 立即冻结订单、拒绝发证并告警。
- 保存最小化审计摘要和 correlation ID。
- 对比许可证产品表、签名价格断言、Karios 订单和微信金额。
- 处理人不得通过直接改数据库绕过差异；需要新的审计化补偿操作。

### 7.4 退款异常

- `PROCESSING` 不等于成功，等待通知或实时查询。
- 仅最终退款成功才把许可证标记 `REFUNDED` 并停止续签。
- 退款服务超时不能盲目重试创建新退款，必须使用原幂等键查询。

## 8. 邮件故障

- SMTP 临时错误：按 outbox 退避计划重试。
- 地址永久错误：进入 dead letter，通知运营。
- SMTP 返回接受但用户未收到：检查 Message-ID、退信、垃圾箱和域名信誉，不重复发送同一明文密钥。
- 需要重发时：管理员执行“轮换并重发”，旧 HMAC 作废，新密钥以新 outbox 发送。
- SMTP 凭据泄漏：立即在供应商撤销/轮换，更新 Sealos Secret，滚动重启 Auth 和 worker，检查异常发信和日志。

## 9. 密钥和证书事故

### 9.1 许可证 HMAC pepper

疑似泄漏时创建 V2 pepper，停止新激活，按用户重新验证或运营轮换密钥。不能仅替换 pepper 而让全部现有密钥静默失效。

### 9.2 授权 Ed25519 私钥

1. 停止签发新 entitlement。
2. 生成新 key 和 `kid`，安全发布包含新公钥的客户端。
3. 服务端拒绝被泄漏 key 签发的新 JTI；评估是否缩短过渡期。
4. 由于离线 token 最长 7 天，记录最坏残留窗口并公告。

### 9.3 Tauri updater 私钥

- 立即冻结 manifest 更新。
- 轮换 updater key，并通过仍受 Authenticode 信任的过渡版本分发新公钥。
- 审计所有近期更新资产和访问日志。

### 9.4 自签名 PFX

- 停止分发，通知测试人员删除旧证书信任。
- 生成新测试证书并重新签署新版本，不覆盖旧资产。
- 自签名证书没有可靠公众撤销覆盖，必须明确沟通影响。

### 9.5 SignPath 账户或项目

- 暂停签名审批和发布流水线。
- 撤销异常成员/凭据，联系 SignPath 支持并保全审计。
- 不用本地私钥伪造 Foundation 正式流程。

## 10. 更新事故与回滚

### 10.1 manifest 指向错误资产

- 立即恢复上一份已知有效且签名正确的 manifest。
- 不替换或覆盖已经发布的同名安装包。
- 确认所有镜像哈希一致后发布修复版本。

### 10.2 新版本启动失败

- 停止 rollout 并保留下载证据。
- 若未发生不可逆项目 schema 迁移，可引导安装上一正式版本。
- 若已经迁移，使用迁移前 `.sttbackup` 恢复到新副本；不得让旧应用直接打开更高 schema。
- 发布修复版本优先于要求用户手工修改数据库。

### 10.3 镜像不一致

- 从更新 manifest 移除异常镜像或让其返回明确非 2xx。
- 比较 GitHub、`updates.karios.tech`、Zot/对象存储的 SHA-256。
- 从经过签名验证的源重新同步，不从未知客户端回传文件。

## 11. 事件分级与记录

| 等级 | 示例 | 初始动作 |
| --- | --- | --- |
| SEV-1 | 私钥泄漏、错误批量发证、支付金额错误、大规模数据丢失 | 立即冻结相关写入/发布，负责人介入 |
| SEV-2 | Auth/激活不可用、邮件队列停滞、备份连续失败 | 30 分钟内响应并启用降级/修复 |
| SEV-3 | 单用户授权、单订单、单项目恢复问题 | 工单追踪，保护原始证据 |

每个事件记录：开始/发现时间、影响、correlation ID、采取动作、数据/密钥接触范围、恢复点、验证结果、负责人和复盘任务。记录不得复制原始密钥、JWT 或密码。

## 12. 恢复完成检查

- [ ] 恢复对象在隔离环境通过完整性和权限检查。
- [ ] 没有重复发送邮件、重复 webhook 或重复发证。
- [ ] Auth、订单、许可证和设备计数与恢复点一致。
- [ ] RLS、AAL2、签名和密钥版本验证通过。
- [ ] 本地项目抽样课表、候选和导出一致。
- [ ] 监控、备份和到期清理已经恢复。
- [ ] 临时凭据、测试域名和隔离数据已安全处理。
- [ ] 事件记录和后续改进任务完成。
