# 账号会员联网授权（2026-09-05）

本方案取代 02、12 文档中的「企业激活码 + 七天离线授权」作为当前实现目标。用户明确选择先做联网校验，以减少配置和操作。

## 用户流程

登录同一个 Supabase 账号 → Rust 请求 STT API 核验会员 → 有效会员自动进入工作台。不输入或领取激活码，不另外购买桌面许可证。

身份服务为 `https://supabase.karios.tech`，会员服务为 `https://fjozndbjkinl.sealosbja.site/api/me/desktop-entitlement`。分别配置在 `config/services.yaml` 的 `identity.endpoint` 和 `license.endpoint`（后者填 API 根地址）。

桌面公开环境变量 `STT_SUPABASE_PUBLISHABLE_KEY` 当前填线上 Supabase 的 Legacy anon key，禁止填 service_role、secret key、JWT_SECRET 或数据库密码。开发脚本读取桌面仓库 `.env`，不再自动使用同级 STT 的本地 key。参照仓库 `.env.example` 配置。

## 可信边界

- access/refresh token 留在 Rust 与 Windows Credential Manager，不返回 Vue。
- API 校验 JWT，并查询 `stt.user_entitlements` 与 `auth.users` 邮箱确认状态；客户端不能指定用户或授权期限。
- 不根据用户可写 metadata 授予会员，也不直接授予所有已登录账号权限。
- 每次进程启动先联网，不加载历史 Mock 授权作为正式权限。
- Rust 内存缓存最长 60 秒，绑定用户和 API 地址，使用单调时钟，不能跨进程恢复。这是校验节流，不是离线许可证。
- 界面每 20 秒复核；Rust 对业务请求和本地服务启动也检查缓存。失败、过期、退出清除授权并关闭本地服务，不删除已保存项目。
- 请求不跟随重定向；远程地址必须 HTTPS，本机联调允许 loopback HTTP。
- 当前不实施多设备数量限制，无授权签名私钥、HMAC pepper 或激活码邮件密钥。

购买按钮打开网页登录页。网页与桌面会话独立，须使用相同邮箱购买；购买后返回桌面重新核验。URL 不传递令牌，不根据浏览器支付结果直接授予权限。

## 发布与验证

GitHub 仓库 Variables 中配置 `STT_SUPABASE_PUBLISHABLE_KEY`。Windows CI 先验证它是公开客户端 key，再通过 Rust `option_env!` 编译进安装包；不会打印 key。安装用户无需配置环境变量。运行时环境变量仍可用于开发覆盖，内置 key 仅用于 `https://supabase.karios.tech`，切换到其他 Supabase 实例必须显式提供对应 key。更换仓库变量后必须重新构建，旧安装包不会自动更新。

先部署配套 STT API/Web 更新，再重打包桌面安装包。只编辑源码不会更新已安装的 0.1.6 安装包。旧 API 没有新接口时，桌面会提示先更新 API，不退回 Mock。

验证范围：API 权益单元/路由测试；Rust 身份与期限验证、内存缓存隔离、本机 HTTP 收发与错误拒绝；Vue 类型检查及构建。线上真实账号完整登录/购买/安装包验收仍须在 API 发布后执行。

旧 Mock 函数和测试夹具保留用于回归，默认身份、会员、支付配置均为 real。SMTP 和更新检查等其他模块仍按原计划，不属于本次会员流程。
