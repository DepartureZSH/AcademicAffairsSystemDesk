# SQLite 版本迁移与迁移前恢复点

## 1. 模块结论

本地项目不再只判断“schema 是否过新”。打开低版本项目时，应用现在会在获得项目排他锁后完成磁盘空间检查、生成并验证 `pre-migration` 完整备份、逐版本事务迁移、SQLite 完整性/外键复核，最后原子更新项目 manifest。任何一步失败都会拒绝打开项目，并保留可独立验证的迁移前备份。

## 2. 版本规则

- `SCHEMA_VERSION` 当前为 2；
- `SCHEMA_V1` 保持不可变，后续版本写入 `MIGRATIONS[target_version]`；
- 新项目按 V1 基线依次应用到当前版本，不产生无意义的迁移备份；
- 旧项目只允许逐版本向前迁移，缺少任一中间迁移立即失败；
- 高于应用支持版本的项目继续以 `ProjectSchemaTooNewError` 拒绝；
- schema 迁移不改变业务 revision，避免把结构升级误判为教务数据变化。

V2 新增 `timetable_template_assignments` 表，为后续按班级、教师、科目、教室和教室类型分配作息模板提供本地存储。该表使用外键、实体类型检查、`all`/实体 ID 一致性检查和实体唯一索引。

## 3. 迁移前保护

迁移前要求可用空间至少为“当前项目目录大小的两倍 + 500 MiB”。恢复点使用既有 `.sttbackup` 格式，记录迁移前的真实 schema 版本，而不是当前应用版本。归档生成后必须完成文件列表、大小、SHA-256、路径穿越、符号链接、压缩比和 SQLite 副本检查，才允许执行 DDL。

所有单版本 DDL 与 `app_metadata.schema_version` 更新位于同一个 SQLite 事务。若 SQL 语法、约束或磁盘操作失败，事务回滚，原 schema 版本和数据保持不变；错误信息包含已保留恢复点的文件名。

## 4. 自动验证

测试会构造真实 V1 项目并验证：

1. 打开时自动创建可验真的 V1 `.sttbackup`；
2. V1→V2 后 assignment 表存在、数据库和 manifest 均为当前版本；
3. 注入失败 DDL 后新增表被回滚、schema 仍为 V1；
4. 即使迁移失败，恢复点仍存在且通过完整归档校验。

该机制是以后新增本地领域表、索引或约束的强制基础，禁止直接修改既有 `SCHEMA_V1` 来假装完成升级。
