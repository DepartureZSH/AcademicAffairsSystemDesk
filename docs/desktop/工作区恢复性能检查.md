# 工作区恢复性能检查

## 发现

“正在恢复工作区”覆盖本地服务启动、健康检查、项目列表读取及已有项目重新打开，不只是数据库恢复。

在本机临时空工作区使用 `Test-FrozenSidecarLifecycle.ps1` 测试，原单文件服务从启动到 ready 为 17076 ms。源码模式仅导入 API 模块约 1.72 秒，同时提前加载 pandas、numpy、OR-Tools、openpyxl、reportlab。空工作区即可复现等待，说明单文件包每次解压及加载运行依赖是一个显著的共同瓶颈，不应直接归因于用户项目损坏或数据量。

## 本次优化

- Python 服务改用目录分发。依赖随安装包安装至 `_internal`，不再每次运行解压到临时目录。保留中文后台程序名和安装器卸载文件清单。
- 区分目录分发的单进程和旧单文件分发的启动器/工作进程 PID，保留原握手校验和退出检测。
- Rust 的阻塞启动工作放到后台线程，不在界面命令线程中等待服务 ready；保留许可证检查、一次性令牌和启动超时。
- 健康检查与项目列表读取并行执行，减少启动链路中不必要的串行等待。

## 实测结果

相同机器、相同临时空工作区测试脚本：原单文件一次 17076 ms；新目录分发首次 8043 ms，随后两次 1241 ms、1254 ms。没有清理操作系统缓存，也没有禁用安全软件，因此首次与后续启动不能视为完全相同缓存条件下的基准。此数值仅测服务启动到 ready，不包含远程身份核验及真实大型项目打开时间。

216 项 Python 测试、34 项 Rust 测试通过。冻结版本全流程验证覆盖排课及 warm start、AI 本地工具、CSV/XLSX/PDF/XML 导出、项目归档和备份恢复，启动与关闭后无残留进程。

## 注意

必须重新打包完整安装器才能获得收益，不能只替换后台 EXE：它依赖同目录 `_internal`。不可删除该目录或从其他版本拷入依赖。此优化纳入 v0.2.9；不修改用户工作区、账户凭据或历史版本安装包。

若部署新版本后仍慢，应分别测量身份核验、本地服务 ready、项目列表与实际项目打开耗时，再决定下一步；本次没有对用户真实项目做数据清理或关闭完整性验证。
