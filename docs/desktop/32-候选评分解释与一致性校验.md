# 候选评分解释与一致性校验

## 1. 模块结论

候选方案页不再只显示一个不可解释的总分。选择任意候选后，界面从本地 SQLite 的 `candidate_metrics` 展示时间偏好罚分、教室偏好罚分、分散/负载罚分、硬约束违例、求解耗时和求解器候选数；评分越低越优。

## 2. 数据来源

算法完成或手工移动通过校验时，候选与以下指标在同一数据库事务中持久化：

- `total_score`；
- `time_penalty`；
- `room_penalty`；
- `distribution_penalty`；
- `elapsed_ms`；
- `candidate_count`。

列表接口一次性读取候选和指标，不为每个候选执行独立查询。指标来自候选生成时的不可变结果，不会依据当前约束重新计算或覆盖历史候选。

## 3. 一致性提示

当前评分模型满足：

`total_score = time_penalty + room_penalty + distribution_penalty`

界面实时检查该关系。相等时解释“越低越优”；不相等时显示醒目的数据一致性警告，要求保留项目报告问题，而不是静默展示错误排名。自动测试也对持久化指标和候选总分执行同一断言。

硬约束违例不折算为软分。只有硬约束零违例候选才会保存和导出；无解轮次仍在单独的冲突诊断中说明原因。

## 4. 验收

- 任意自动排课候选返回完整 `metrics` 对象；
- 三类罚分之和等于候选总分；
- 手工调整候选复用相同指标持久化路径；
- 界面展示耗时和候选数，但不把它们计入总分；
- 候选比较仍使用总分差，评分详情解释该总分来源；
- Python、Vue 和 Rust 回归继续通过。
